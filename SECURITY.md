# Security model

Kern binds a merge decision to evidence about one exact commit. It does not make agents, patches or hosts safe in general.

## Trust

- **Untrusted:** agent code and output, repository text read by the agent, executor handoff data, and PR bodies.
- **Trusted per role:** the host, kernel, Docker daemon, gVisor, the pinned Docker/git/runsc binaries, the node image, operator policy, and the role's storage.
- **Local box (developer machine):** the developer's container engine and the agent image they pin. The box protects the developer's machine from the agent; it is not part of the merge guarantee, which rests on the verifier's signature.
- **Verifier-only:** check definitions and signing authority. The executor holds only the verifier's public key.
- **Promoter-only:** publication credentials, the consumed-run ledger, and the reviewer's `expected.json`.

## Guarantees

- **Executor sandbox.** Read-only root, project and Kern binary. Writes go only to tmpfs for the granted directories. No network, no host credentials, no Docker socket, no git metadata. UID 1000, all capabilities dropped, `no-new-privileges`, and memory/swap/PID/CPU/time limits. The daemon's own inspection of each container is checked before it starts.
- **Capture.** After the agent exits, the in-sandbox runner (PID 1) kills every other process in the namespace before reading output. It refuses symlinks, hardlinks, special files and over-budget output, and opens every file with `O_NOFOLLOW`. The container must be removed before any byte is accepted.
- **Handoff.** A git bundle with exactly two refs (base and candidate) and no prerequisites, at most 64 MiB. Objects are fsck-checked on import, and the candidate's manifest must match before anything is labelled imported.
- **Verification.** The verifier re-checks paths, protected files, change budget and the capability diff. Its own cases and the project's test suite run on the exact commit, each in a fresh no-network gVisor sandbox, on a throwaway in-memory copy of the snapshot; the shared dependency install stays read-only, with per-run in-memory cache folders. The expected answers never enter the sandbox.
- **Attestation.** An Ed25519 DSSE envelope over an in-toto Statement (SLSA verification summary). It binds commit, base, manifest, contract, Kern version, verifier configuration, builder identities (which pin each role's exact Kern binary), deployment, image, dependency tree digest and the complete check set. A checker needs the same Kern version and capability policy as the verifier, not the same binary. Verifiers rebuild the canonical statement and require byte equality. Lifetime is one hour for promotion.
- **Promotion.** Values come from independent expectations only. Branches are create-only and run-specific. An authorization is reserved durably before the first mutation and stays consumed even after a failure or branch deletion.
- **Behaviour diff.** The verifier runs every check on the base commit as well, records network destinations, DNS names, started programs and environment reads in both runs, and refuses a candidate that newly reaches the network, starts a new program, enumerates the environment or reads a secret-looking variable, unless the task contract lists it. The result is a signed `behavior` check.
- **Hosted verifier.** `kern serve` binds to loopback only (TLS belongs in a reverse proxy), stores bearer tokens as SHA-256 hashes per repository, authenticates before revealing which repositories it serves, verifies only against contracts it holds (matched by digest), runs one verification at a time, caps connections and request sizes, and refuses to start if its published key differs from its signer.
- **Audit log.** Decisions are appended as hash-chained JSON lines under an OS file lock; `kern audit` detects edited, removed or reordered entries, and `kern report` escapes all recorded text.
- **Local box.** The agent runs in a Linux container (Docker, Podman or Rancher Desktop; gVisor whenever Docker has `runsc`). Its workspace is the only writable host folder; the image and every mount are read-only; home and `/tmp` are private memory filesystems. All capabilities are dropped, `no-new-privileges` and seccomp apply, process and IPC namespaces are private, no host devices are passed, and the contract's memory (with no extra swap), process and time limits apply. There is no network unless the job grants it. Only the environment variables a job lists are passed, by name, so their values never appear on a command line. Before the agent starts, Kern compares the engine's own description of the container with what it asked for and refuses to run on any difference, including limits a rootless engine ignores and variables an engine adds by itself (such as proxy settings). A run whose container never started is refused. The container is removed before any output is read, and output is read with symlink, special-file and size refusals. Ctrl+C, SIGTERM, a closed terminal or the time limit kills the container, and a detached watchdog removes it as soon as the Kern process that started it ends for any reason. Agent output is relayed with each line marked and terminal control characters removed, so it cannot imitate Kern's verdict.
- **Merge check.** Runs from the base branch's workflow. It re-verifies the signature against the trusted key in the base commit and requires attested head == PR head and attested base == PR base. It recomputes the contract and capability checks.
- **Re-verification on push.** Only with a hosted verifier configured, and only for a same-repository `kern/*` pull request whose description carries a proof the trusted key signed for the same run. The trust root is the base branch's current tip as GitHub reports it. The pushed change is moved onto that tip file by file from GitHub's merge base (a file both sides changed is refused), written as one deterministic Kern commit, verified by the hosted verifier under the same run, and checked again by the gate exactly like any Kern pull request. Only then does the branch move, with a lease on the pushed commit, and the new proof and check are published. The GitHub token reaches git only through the environment, scoped to the GitHub server; the verifier token goes only to the hosted verifier. A merge-queue group passes only when its tree is the verified commit's tree on the verified base, or, with a hosted verifier, when the group's tree on its base is verified again under the same run.
- **Proof of honest fix.** When a version 4 contract has a `tests` section, existing test files are either locked at every gate (local box, intake, verifier, merge check, deploy gate and merge audit) or, by default, may change only when the verifier shows that the old tests still pass on the new code and that every planted bug they caught is still caught (a bug counts as lost only when the result repeats); no change may touch the test runner's settings, new test files may not skip or focus tests, and code outside the tests may not use test-runner globals, change an assertion library or check whether tests are running. The verifier then reads the runner's own report, test by test, from runs in a gVisor sandbox without network: the existing suite on the old code, everything on the new code, the old tests alone on the new code whenever tests were added or rewritten (so answers cannot depend on which tests ran first), and for a bug fix everything on the old code with the new tests added. Every test that passed before must still run and pass, nothing else may fail or be newly skipped, and a bug fix needs a new test the runner reports failing on the old code. A test that already failed on the old code must still run but is set aside, and then planted bugs are judged by the report: only a failure of another test catches one. A run without exactly one complete report, a test that could not load and a test that could not run never count as proof. The result is a signed `honest-fix` check that every checker requires.
- **Comparison of the old and the new code (contract version 5).** The verifier calls the exported functions of the changed modules and of their importers with the same arguments on the old and the new code, twice each, in a gVisor sandbox without network, with a fixed clock and seeded randomness; every function gets the same calls on both sides. Module code runs only in worker threads. The probe's main thread, which module code never reaches, decides which calls belong to the stated change and whether the task's examples hold, accepts a worker's messages only with a key the worker deleted before the module loaded, and prints exactly one report, after every worker has stopped, to the stdout it started with. A run without exactly one report, a probe that crashes, a call the new code never answered and a call that answers differently on two runs of the old code never count as "the same"; values are compared whole, with a hash covering whatever is cut short for display. Refused whatever the task states unless its delta names it: a new crash or hang where the old code answered (on either run of the new code), calls the old code answered that the new code leaves unanswered, a module or app that no longer starts, a deleted file, a removed export or one that is no longer a function, new code that calls file-deleting functions, a route that now lets in a role it refused or that did not exist for it, and (from the behaviour recorder, in checks, tests and probes alike) a newly deleted or overwritten file of the repository. With a stated delta, any other difference (including an input the old code refused that now gets an answer, and an error of another kind; an error whose words alone changed is listed, not refused), a failing example, a much slower function and more paid API calls are refused too. Behaviour that only calling the new code shows is reported as the code's, not the tests'. In a dependency change every package keeps its identity (no `npm:` alias of another package, no tarball other than the package's own of that version), and moves are compared old lockfile against new lockfile, each installed on its own. The result is a signed `compare` check whose evidence is the comparison; a pull request description carries it, and the merge check shows it only when the signed proof covers exactly that comparison, with every value from the code inside code formatting.
- **Agent feedback.** Instructions tell an agent what to change in the code, never how to loosen the gate, and what the agent is handed carries neither the raw reason nor the `allow` hints. A block is explained only when its message matches a known message exactly; values taken from it go inside code formatting or must be plain numbers. Only problems an agent can fix are retried, within a cap, and every attempt stays on record. PR comments count only Kern's own earlier comments, one attempt per rejected commit, keep text taken from the change inside code formatting, carry a machine-readable block that cannot break out of its code fence, and never change the verdict.
- **Merge audit.** `kern audit-merges` reads the branch's whole first-parent history and places changes by their order on it, so a false commit date cannot hide a change. It counts only pull requests merged into the audited branch, re-verifies each agent proof with the same checks as the merge and deploy gates, requires the merged commit to have the verified commit's tree and the verified base as its first parent, can insist on a verifier key the auditor supplies, refuses shallow and partial clones, escapes all recorded text in HTML and neutralises spreadsheet formulas in CSV.

## Known limits

- **Agents can abort their own run.** Under gVisor, an agent can signal the runner (PID 1) and abort its run. The run fails closed and nothing is captured.
- **Dependency setup has network access.** It sees only `package.json` and the lockfile, runs `npm ci --ignore-scripts` with every package pinned to one registry host by integrity, and forces TLS. Packages with only legacy SHA-1 pins are counted and disclosed, not rejected.
- **Single-VM mode shares one kernel.** Executor, verifier and promoter share a kernel and a Docker daemon, so a gVisor escape there could reach the signing key. Use `multi-machine` deployment and a KMS/HSM signer where that matters. Machine separation is checked from self-reported identities; it is not hardware attestation.
- **The capability check is syntactic.** It blocks new authority. Misuse of authority a module already holds needs tests and review. Identifiers are resolved with `oxc_semantic`; `tests/redteam.rs` tracks known evasions and the accepted false blocks. A new file is judged against its whole directory's authority.
- **The behaviour diff is advisory against hostile code.** Its recorder runs inside the code under test, which can tamper with it, and it only observes programs started from Node. It reliably catches unintended new behaviour, not deliberate evasion; gVisor-level tracing is the tamper-proof follow-up.
- **The audit chain cannot detect truncation of its newest entries on its own.** Anchor the head hash printed by `kern audit` elsewhere.
- **The local box is a container, not a VM.** Without gVisor the agent shares the kernel of the engine's Linux host or VM with the engine itself, so a kernel exploit can escape the box. A granted network is unrestricted outbound access: an agent that holds an API key can send what it reads in its workspace anywhere, and on Docker Desktop it can also reach services listening on the developer's own machine through `host.docker.internal`. Kern trusts the engine's report of its own configuration.
- **Passing checks is not proof of correctness or intent.** Code can be tailored to known tests.
- **The comparison samples.** It tries the old tests' own arguments, unusual values, values from the source and seeded mixes of them, not every input; behaviour behind an input nobody generates, a database or a network answer can differ unseen. Code under test shares its worker thread with the part of the probe that calls it and writes down its answers, so code written to fool the probe can make its answers look like the old code's, as code that detects the probe always could. It cannot sign the probe's messages, change which calls the task states, decide whether an example holds, leave calls unanswered unnoticed or replace the report; the gVisor sandbox and the capability diff (which refuses new use of `worker_threads`, `inspector`, `vm` and `process.kill`) bound what it can reach. Modules that do not load in Node without a build step are reported as not checked, not as unchanged.
- **Tests that fail before the change are set aside.** They can neither block nor prove anything, so a change can leave them broken; the evidence lists them for review. A suite where nothing passes before the change is refused.
- **Re-verification gives the pull-request workflow write access.** With it on, the workflow token can push (`contents: write`) and report checks (`checks: write`). Kern pushes only to the pull request's own `kern/*` branch, with a lease on the commit it verified, and runs no pull-request code in that job; protect the base branch so that token cannot push there.
- **The safety net for rewritten tests is a sample.** At most 40 planted bugs per change, from a small set of edits, decide whether rewritten or removed tests still catch what the old ones caught. A loss outside that sample, or behaviour no planted bug touches, goes unnoticed; the old tests still have to pass on the new code either way.
- **The proof of honest fix trusts the test runner's report.** Tests that stop running, get skipped or fail show up however that was done, but code running inside the test process can still tamper with the runner, its report or the assertion library in ways Kern does not recognise and fake a pass. The operator's hidden checks and review remain the backstop.
- **Feedback can help a hostile agent probe the gate.** Telling an agent why it was blocked also tells it what was detected. Retries are capped, every attempt is kept on record, and the capability and behaviour checks do not rely on secrecy.
- **The merge audit trusts GitHub's record of which pull request merged each commit.** That decides how a change is classified; the proof itself is verified cryptographically against the clone's own objects.
- **The installers trust the release they come from.** `install.sh` and `install.ps1` check the binary against that release's `SHA256SUMS`, which catches a corrupted or swapped download, not a release that was itself compromised. To check where a binary came from, verify its build-provenance attestation (`gh attestation verify <file> --repo jastijayakrishna/Kerner`); the merge-gate action pins exact binary digests in `action.yml`, so pinning the action by commit pins the binary. Enable immutable releases so published files cannot change.
- **Kern's status and Kern's build share the repository with its other workflows.** Any workflow in a repository can set a commit status and write to GitHub's Actions cache, so a pull request that adds or changes a workflow could post its own `Kern` status or plant a build that Kern's workflow then reuses. Kern's receipt lists every changed workflow as needing a look, and `kern receipt verify` checks GitHub's signature for Kern's own workflow; still, require a code owner's review for `.github/workflows/`, and where GitHub offers it, require Kern's workflow in a ruleset rather than its status. Pinned release binaries take the build cache out of this path.
- **Publication is not atomic.** GitHub push and PR creation are separate requests. Mismatches fail and leave state for manual reconciliation. CI triggered by a pushed branch is outside Kern's control.

## Reporting

Report vulnerabilities privately to the repository owner. Never include credentials.
